# Comparing a TINTOlib pull request with `main`

This guide explains how to test whether a pull request changes the images
generated by TINTOlib.

The comparison uses:

- a clean checkout of `origin/main` as the baseline;
- a separate checkout of the pull request;
- isolated Python environments for the two checkouts;
- identical preprocessed train, validation, and test data;
- identical method parameters and random seeds;
- pixel-level comparison of corresponding images.

The generated data, images, environments, and reports are local test artifacts.
Do not commit them.

## Directory layout

The commands below assume this layout:

```text
dev/
├── TINTOlib/          # pull-request checkout
└── TINTOlib-main/     # clean origin/main baseline
```

Run all commands from `TINTOlib/` unless stated otherwise.

## Requirements

- Windows PowerShell
- Git
- Python 3.10 or newer

Python 3.10+ is required because the current dependency set includes a Numba
version that does not install on Python 3.9.

## One-time setup

These steps only need to be completed once on a machine.

### 1. Create the clean `main` worktree

From the pull-request checkout:

```powershell
git fetch origin
git worktree add ..\TINTOlib-main origin/main
```

`git worktree` is preferable to cloning the repository again. Both directories
share Git objects, but their checked-out files remain independent.

### 2. Create isolated environments

```powershell
python -m venv .venv
python -m venv ..\TINTOlib-main\.venv
```

Install each checkout into its own environment:

```powershell
.\.venv\Scripts\python.exe -m pip install -e .
..\TINTOlib-main\.venv\Scripts\python.exe -m pip install -e ..\TINTOlib-main
```

If dependencies are already provided by a shared environment and disk space is
limited, the environments can instead be created with
`--system-site-packages`, followed by editable installs using `--no-deps`.

### 3. Verify isolation

Run the first command from `TINTOlib/`:

```powershell
.\.venv\Scripts\python.exe -c "import TINTOlib; print(TINTOlib.__file__)"
```

Run the second command from `TINTOlib-main/`:

```powershell
.\.venv\Scripts\python.exe -c "import TINTOlib; print(TINTOlib.__file__)"
```

The paths must point to different worktrees. Do not continue if both commands
resolve to the same directory.

## Preparing comparison data

Both versions must receive exactly the same values. The target is stored in the
final column for classification and regression datasets.

The repository provides `prepare_splits.py`, which:

- uses a fixed random seed;
- creates 70% train, 15% validation, and 15% test splits;
- stratifies classification splits;
- fits preprocessing only on the training split;
- applies the fitted preprocessing to validation and test data.

### Boston regression

```powershell
.\.venv\Scripts\python.exe scripts\version_comparison\prepare_splits.py `
  --data Dataset\Regression\boston.csv `
  --preprocess-config configs\preprocess\boston.json `
  --output comparison_data\boston `
  --problem regression `
  --seed 64
```

### Credit approval binary classification

```powershell
.\.venv\Scripts\python.exe scripts\version_comparison\prepare_splits.py `
  --data Dataset\Binary\credit-approval\credit-approval_cleaned.csv `
  --preprocess-config configs\preprocess\credit-approval_cleaned.json `
  --output comparison_data\credit-approval_cleaned `
  --problem classification `
  --seed 64
```

### CMC multiclass classification

```powershell
.\.venv\Scripts\python.exe scripts\version_comparison\prepare_splits.py `
  --data Dataset\Multiclass\cmc\cmc.csv `
  --preprocess-config configs\preprocess\cmc.json `
  --output comparison_data\cmc `
  --problem classification `
  --seed 64
```

The resulting files are stored under:

```text
comparison_data/<dataset>/
├── train.csv
├── val.csv
└── test.csv
```

The splits can be reused across pull requests as long as the source dataset,
preprocessing configuration, scikit-learn version, and seed have not changed.

## Testing a new pull request

Assume the GitHub pull-request number is `42`.

### 1. Make sure local work is safe

```powershell
git status
```

Commit or stash unrelated work before switching branches. Never discard local
changes merely to run this test.

### 2. Update the baseline

```powershell
git fetch origin
git -C ..\TINTOlib-main checkout --detach origin/main
```

Record the baseline commit for the report or pull-request description:

```powershell
git -C ..\TINTOlib-main rev-parse --short HEAD
```

### 3. Check out the pull request

For a GitHub pull request by number:

```powershell
git fetch origin pull/42/head:pr-42
git switch pr-42
```

If the pull request is available as a named remote branch:

```powershell
git fetch origin
git switch --track origin/name-of-pr-branch
```

If the local PR branch already exists, update it using the normal workflow for
that branch instead of recreating it.

### 4. Refresh the editable installations

```powershell
..\TINTOlib-main\.venv\Scripts\python.exe `
  -m pip install -e ..\TINTOlib-main --no-deps

.\.venv\Scripts\python.exe `
  -m pip install -e . --no-deps
```

Use a normal install without `--no-deps` if the pull request changes project
dependencies.

### 5. Run the comparison

#### Boston

```powershell
scripts\version_comparison\run.ps1 `
  -PreviousPython ..\TINTOlib-main\.venv\Scripts\python.exe `
  -CurrentPython .\.venv\Scripts\python.exe `
  -PreviousLabel main `
  -Splits comparison_data\boston `
  -Dataset boston `
  -Problem regression
```

#### Credit approval

```powershell
scripts\version_comparison\run.ps1 `
  -PreviousPython ..\TINTOlib-main\.venv\Scripts\python.exe `
  -CurrentPython .\.venv\Scripts\python.exe `
  -PreviousLabel main `
  -Splits comparison_data\credit-approval_cleaned `
  -Dataset credit-approval_cleaned `
  -Problem classification
```

#### CMC

```powershell
scripts\version_comparison\run.ps1 `
  -PreviousPython ..\TINTOlib-main\.venv\Scripts\python.exe `
  -CurrentPython .\.venv\Scripts\python.exe `
  -PreviousLabel main `
  -Splits comparison_data\cmc `
  -Dataset cmc `
  -Problem classification
```

`run.ps1` performs three operations:

1. Generates images for methods shared by `main` and the pull request.
2. Compares corresponding decoded pixel arrays.
3. Smoke-tests methods listed in `current_only.json` using the pull request.

## Reading the results

Results are written under:

```text
comparison_results/<dataset>/
├── main/
├── current/
├── current-only/
└── comparison.json
```

Each generation directory contains a `run_summary.json`. Every tested method
should have:

```json
"status": "passed"
```

For a pixel-identical comparison, `comparison.json` should contain:

```json
{
  "missing_after": [],
  "new_after": [],
  "shape_mismatches": 0,
  "mean_mae": 0.0,
  "max_abs_error": 0.0
}
```

Also verify that `exact_matches` equals `common_images`.

A difference is not automatically a defect. A pull request may intentionally
change an algorithm. When images differ, review:

- which methods and files changed;
- whether image counts and dimensions still match;
- whether the change was intentional;
- dependency and font differences;
- random-seed handling.

Record the baseline commit, pull-request commit, dataset, configuration, and
comparison summary in the pull-request description.

## Configuration files

`configs/version_comparison/shared_methods.json` contains parameters used by
both versions. Keep these parameters identical for a direct comparison.

`configs/version_comparison/current_only.json` contains smoke tests for methods
that should only be run in the checkout under test.

Do not change a shared parameter only for one version. If an API name changes,
adapt it in `generate.py` while preserving the same effective behavior.

Add a current-only configuration when a pull request introduces a new method.
Move it into the shared configuration after the method is merged into `main`.

## What to commit

Commit reusable source files:

```text
scripts/version_comparison/
configs/version_comparison/
configs/preprocess/
```

Do not commit local artifacts:

```text
.venv/
comparison_data/
comparison_results/
SyntheticImages/
*.pkl
generation_times.json
```

The repository's local Git exclusions should keep `comparison_data/` and
`comparison_results/` out of `git status`. Generated images and environments
must remain local.

## Testing a release tag instead of `main`

To use a release as the baseline, create a worktree for that tag:

```powershell
git worktree add ..\TINTOlib-v1.2.2 v1.2.2
python -m venv ..\TINTOlib-v1.2.2\.venv
..\TINTOlib-v1.2.2\.venv\Scripts\python.exe `
  -m pip install -e ..\TINTOlib-v1.2.2
```

Pass that environment to `-PreviousPython` and use the tag as
`-PreviousLabel`. The rest of the workflow is unchanged.
